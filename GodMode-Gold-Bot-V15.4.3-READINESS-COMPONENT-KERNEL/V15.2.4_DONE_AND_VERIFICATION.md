# V15.2.5 Priority Intent Execution

Build: `V15.2.5-PREDICTOR-STATUS-RECOVERY`

## Evidence from the reported Telegram alert

The reported message used all three legacy signatures:

- `MOMENTUM SPIKE DETECTED — WATCH RETEST`
- fixed `Spike quality: 82%`
- no build ID footer

Those strings are absent from the V15.2.3 and V15.2.5 runtime alert generator. The screenshot therefore proves that an older backend process produced the alert. A newer browser page can be open while an old Python process still owns port 8000, so clearing the browser cache alone cannot correct this condition.

## Confirmed latency and execution gaps

1. **Stale backend ownership:** the launcher previously recognised only an old `uvicorn app:app` command line. Older `python app.py` launch styles could remain active.
2. **Sequential background workload:** the normal auto loop performs trading, Telegram/chart work, breakout maintenance and journal analysis in sequence. A nominal 0.5-second loop could therefore be delayed by unrelated work.
3. **Repeated terminal history reads:** the predictor requested 90 M5 and 90 M15 candles on every scan. MT5 terminal IPC is serialized, so this created queueing and laptop load.
4. **Duplicate decision pass:** the priority detector qualified a candidate and the execution path then recalculated the predictor before submission. Price or direction could change between those passes.
5. **Repeated full tick windows:** each scan previously reloaded the complete tick window rather than only unseen ticks.
6. **Unserialized tick-range call:** `copy_ticks_range` was omitted from the bridge IPC guard list.
7. **Synchronous AI delay:** when enabled, the external AI auditor could add seconds to the critical entry path.
8. **Uncalibrated forecast veto:** a heuristic V15 forecast could suppress an otherwise valid deterministic intent probe before enough outcomes existed for calibration.
9. **Unclear fallback message:** the mature-move notification looked like the predictor had only just detected the move. It did not disclose the early-stage state or execution blocker.
10. **Hidden execution state:** the operator could not see whether the candidate was blocked by Live Trading, Dry Run, Auto Trading, validation, certification, cooldown or another gate.

## Implemented architecture

### Phase 1: exact-build process ownership

Done criteria:

- The active backend identifies itself as `service=godmode-backend` and the exact build ID.
- The launcher closes a stale GodMode backend even when it was not launched with the current uvicorn command style.
- Unrelated applications using port 8000 are never terminated automatically.
- The launcher verifies both `/api/health` and `/api/fast-sniper/status` before opening the dashboard.
- `VERIFY_ACTIVE_BUILD.bat` provides an independent operator check.

Status: **Done**

### Phase 2: independent Priority Intent lane

Done criteria:

- Priority scanning runs independently of Telegram, chart rendering and maintenance work.
- Default interval is 0.25 seconds.
- Only anticipatory `TAKE_TRADE` decisions are dispatched.
- Duplicate candidate attempts are throttled and the normal execution ledger remains authoritative.
- All existing execution, broker, spread, news, risk, stop and certification gates remain active.

Status: **Done**

### Phase 3: detect-to-submit continuity

Done criteria:

- The exact decision and market snapshot that qualified the intent are passed into order execution.
- Execution does not rerun the predictor before submitting the candidate.
- Candidate first-seen time, scan latency, dispatch latency and end-to-end latency are recorded.
- Source tick age is preserved in the candidate record.

Status: **Done**

### Phase 4: MT5 IPC and data-path optimisation

Done criteria:

- Tick windows are incremental after warm-up.
- M5 context is cached for 0.50 seconds and updated from the current live price between refreshes.
- M15 context is cached for 5 seconds.
- `copy_ticks_range` and `copy_rates` are both protected by the MT5 IPC lock.
- Early Intent and Early Impulse share the same canonical tick buffer.

Status: **Done**

### Phase 5: non-blocking anticipatory governance

Done criteria:

- Anticipatory decisions do not wait for a synchronous external AI audit.
- An uncalibrated V15 forecast cannot veto a deterministic anticipatory candidate.
- A calibrated V15 model can still apply its configured safety veto.
- Existing deterministic safety controls remain authoritative.

Status: **Done**

### Phase 6: truthful diagnostics and Telegram evidence

Done criteria:

- The old fixed 82% alert text is not generated by this build.
- Mature movement alerts are labelled `POST-MOVE DIAGNOSTIC — EARLY ORDER NOT SENT`.
- The diagnostic states Early Intent and Early Impulse probability, displacement, tick age, tick-fetch latency, execution readiness and the most recent priority result.
- Every rich Telegram alert includes the exact build ID.
- The Settings panel shows Priority Intent state, blocker, tick age, fetch latency and dispatch timing.

## Operational interpretation

A 0.76 ATR notification is not itself proof that the early engine first woke up at 0.76 ATR. In this release it is explicitly a post-move diagnostic. The useful fields are now:

- Early Intent state and probability
- Early Impulse state and probability
- candidate first-seen displacement
- tick age and fetch latency
- priority scan and dispatch latency
- exact execution blocker
- active build ID

This distinguishes detection latency from policy blocking. For example, a candidate can be detected at 0.09 ATR but blocked because Auto Trading is OFF. That is not a slow predictor and should not be “fixed” by lowering thresholds.
