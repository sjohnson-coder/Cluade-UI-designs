# GodMode Gold Bot V15.4.3 Readiness Component Kernel

Build ID: `V15.4.3-READINESS-COMPONENT-KERNEL`

## Confirmed root causes

1. The previous readiness worker executed one monolithic `_authoritative_readiness()` call containing MT5 market-state, Tick Guard, certification, validation, persistence, runtime-health and execution-ledger work.
2. The complete aggregate had a fixed 0.8-second deadline. One slow dependency timed out the entire cycle and rotated the executor repeatedly.
3. Timed-out native work could continue after executor rotation, allowing abandoned threads to accumulate while new readiness cycles repeated the same work.
4. Live order admission and runtime-health endpoints still called the same synchronous readiness function, so readiness latency could affect entry admission and API responsiveness.
5. `_fast_sniper_decision()` referenced an undefined `regime` name in the adaptive body gate. The missed-move autopsy called this path and produced the recorded `NameError: name 'regime' is not defined`.

## Implemented corrections

### Componentised readiness

Readiness is split into independently refreshed components:

- MT5 status
- Market state
- Tick Guard
- Live certification
- Validation
- Unresolved broker commands

Each component has its own interval, timeout, freshness budget, last-success payload, error state and in-flight protection.

### No repeated submission of timed-out probes

A timed-out component remains marked in flight until the original worker actually completes. The scheduler does not submit another copy of the same probe. This prevents unbounded thread/executor accumulation.

### O(1) aggregate snapshot

The readiness aggregate only composes cached component values, runtime-health state and local configuration. It performs no MT5, certification, Tick Guard, validation or ledger I/O.

### Trading-path isolation

- Pre-live order admission uses the cached readiness snapshot.
- Auto-control status uses the cached readiness snapshot.
- Runtime-health reporting uses the cached readiness snapshot.
- Browser readiness polling never triggers deep readiness work.

A stale critical component remains fail-closed and is named explicitly in `executionBlockers`.

### Manual refresh feedback

The manual refresh endpoint refreshes components concurrently and reports:

- successful refresh
- component still running
- last-known-good data retained

The refresh result cannot be overwritten by the cached application-health `ok` value.

### Missed-move autopsy repair

The adaptive Fast Sniper body gate now reads `_regime_info["regime"]`. It no longer references the undefined `regime` name.

### Runtime diagnostics

`/api/runtime/lanes` now exposes every readiness component with:

- status
- freshness
- duration
- attempts
- successes
- failures
- timeouts
- skipped duplicate submissions
- current in-flight state
- last error

## Safety note

Automated verification can prove the tested code paths and package integrity. It cannot prove that no defect can occur under every Windows, MT5, broker, network or hardware condition. Keep validation and broker protections active during the first demo forward run, and inspect `/api/runtime/lanes` if any component reports stale or timed out.
