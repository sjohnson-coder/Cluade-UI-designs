# V15.3.2 Sustained Burst Intelligence

Build: `V15.3.2-NONBLOCKING-RUNTIME-RECOVERY`

## Purpose

This release upgrades Protected Burst without weakening the existing V15.2.9 Qualified Peak Runner. Burst remains an add-on to a profitable base trade. It cannot create the first market position and it cannot bypass broker admission, news, spread, validation, certification, position-count or risk controls.

## Implemented architecture

### 1. Canonical Telegram state resolver

Telegram Burst controls use the same fully resolved configuration as the execution engine. An empty or partially populated stored configuration can no longer make Telegram display Burst OFF while the runtime defaults resolve it as enabled.

### 2. Correct MT5 account classification

The MT5 bridge now exposes native account trade mode and normalized account status:

- `DEMO`
- `CONTEST`
- `REAL`
- `UNKNOWN`

The Burst demo-only gate consumes this normalized state instead of guessing from missing dictionary fields.

### 3. Immediate adaptive batch

When all gates pass, Burst submits one immediate batch:

- two legs at the standard qualifying tier;
- three legs only when both confidence and continuation satisfy the stronger tier.

The batch is preflighted before submission. When atomic rollback is enabled, a partial submission failure triggers closure of already opened batch legs and records the failed-batch lock.

### 4. Deterministic break-even arm

Burst eligibility is measured against the actual deterministic protection threshold, using the live trade entry, initial risk, configured break-even R/points and protection settings. It no longer treats spread plus slippage as the break-even target.

The default arm point is 85% of the distance to the true protection threshold.

### 5. Sustained evidence

Confidence and continuation must remain qualified across a configurable sequence of scans within a bounded window. The evidence tracker rejects:

- insufficient scan count;
- expired evidence windows;
- confidence deterioration beyond the configured limit;
- continuation deterioration beyond the configured limit;
- direction changes;
- base-trade changes.

A transient one-scan score spike cannot launch the whole batch.

### 6. Rounded basket-risk enforcement

All intended leg volumes are normalized to the broker minimum, maximum and lot step before final approval. The engine then recalculates the aggregate cash risk of the actual rounded basket.

The batch is rejected when:

- one leg violates broker volume rules;
- total rounded volume exceeds the Burst limit;
- aggregate rounded risk exceeds the Burst account-percentage budget;
- any planned stop is invalid;
- an execution-safety preflight fails.

### 7. Independent Burst lifecycle

Every Burst leg is tagged and managed separately from the base position:

- `BURST_PROBE`
- `BURST_CONFIRMED`
- `BURST_RUNNER`
- `BURST_DEFENSIVE`

Burst probes use stricter fast-fail, break-even and trail settings. They cannot use loss-side recovery widening or breathing. Confirmed and runner legs may use profitable deterministic runner management while preserving the stricter Burst invalidation rules.

### 8. Complete live gate trace

The dashboard polls a lightweight Burst status endpoint and displays every condition as passed, waiting or failed. The trace includes:

- account mode;
- demo-only permission;
- Burst enabled state;
- base-position presence and direction;
- base-trade protection state;
- deterministic break-even arm progress;
- confidence and continuation;
- sustained scan progress;
- probability deterioration;
- market, news, spread, chop, M15 and MTF gates;
- position capacity;
- validation/certification and complex-entry permission;
- planned batch size and rounded basket risk;
- cooldown, campaign and failed-batch locks;
- latest execution or rollback result.

`canFire` is not used as an ambiguous static readiness claim. The trace distinguishes structural arming from complete execution readiness.

## Safety defaults

The packaged configuration remains deliberately disarmed:

- live trading disabled;
- auto trading disabled;
- dry run enabled;
- local runtime certification required;
- deployment mode `LIVE_RESTRICTED`;
- one open position maximum under restricted mode;
- complex entries disabled under restricted mode.

These defaults mean Burst will not fire immediately after extraction. This is intentional. It must be validated on a demo account, certified, and explicitly permitted before multi-leg execution becomes possible.

## Live validation still required

Automated tests cannot prove broker-specific behaviour. Before live deployment, verify:

- MetaEditor compilation of the supplied Tick Guard;
- account `trade_mode` on the target broker;
- lot minimum and step rounding;
- atomic rollback behaviour under rejected orders;
- real spread, slippage and freeze levels;
- batch submission latency;
- restart and MT5-disconnection recovery;
- sustained-scan behaviour during active XAUUSD conditions;
- aggregate basket risk on the actual account currency and contract specification.
